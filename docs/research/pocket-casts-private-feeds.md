# How Pocket Casts handles a private feed

Research for [#108](https://github.com/ericmasiello/skills/issues/108), part of the podcast-feed wayfinder map ([#106](https://github.com/ericmasiello/skills/issues/106)). Researched 2026-11-25.

Sources are Pocket Casts' own help center, Pocket Casts' open-source apps, and Apple's podcast RSS documentation. Code links are pinned to the commits read:

- Android: [`Automattic/pocket-casts-android@09b46eb`](https://github.com/Automattic/pocket-casts-android/tree/09b46eb33c5e92833eee78ef1317def953161494)
- iOS: [`Automattic/pocket-casts-ios@bd133d3`](https://github.com/Automattic/pocket-casts-ios/tree/bd133d328464a8e2ee792a9371c697fb568458e3)

The server side (the feed parser and directory) is closed source. Anything about it that the help center doesn't say is marked **inferred**.

## Answer

Pasting a feed URL into the Pocket Casts search bar submits the feed to Pocket Casts' servers, which fetch and parse it. The feed is kept out of public search only if it carries `<itunes:block>Yes</itunes:block>`. With that tag, Pocket Casts classifies the show as private: it is left out of search and sharing is turned off. The phone never reads the feed. It downloads and streams the MP3s itself, straight from the enclosure URL. Pocket Casts' servers do not proxy or cache episode audio. So both the feed URL and the MP3 URLs must be publicly reachable over HTTPS: the feed for Pocket Casts' crawlers, the MP3s for the phone on cellular.

## Findings

### 1. Discoverability

**Adding by URL submits the feed to Pocket Casts' directory.** There is no separate "Add by URL" option. You paste the URL into the search bar, and "if the podcast isn't in Pocket Casts yet, this also submits it to our system so we can start parsing it" ([Podcast Search](https://support.pocketcasts.com/knowledge-base/podcast-search)). The app sends the search term, URL or not, to `POST https://refresh.pocketcasts.com/podcasts/search` ([`ServiceManager.kt` L40–48](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/servers/src/main/java/au/com/shiftyjelly/pocketcasts/servers/ServiceManager.kt#L40-L48), [`build.gradle.kts` L299](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/build.gradle.kts#L299)). The server answers with a podcast record and an `is_url` flag ([`DataParser.kt` L49–70](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/servers/src/main/java/au/com/shiftyjelly/pocketcasts/servers/DataParser.kt#L49-L70)). iOS posts to the same endpoint ([`PodcastSearchTask.swift` L146](https://github.com/Automattic/pocket-casts-ios/blob/bd133d328464a8e2ee792a9371c697fb568458e3/Modules/Sources/PocketCastsServer/Public/Search/PodcastSearchTask.swift#L146)). When the term starts with `http`, the app also skips the episode search ([`SearchHandler.kt` L265](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/features/search/src/main/java/au/com/shiftyjelly/pocketcasts/search/SearchHandler.kt#L265)).

**`<itunes:block>Yes</itunes:block>` is what makes a feed private.** Pocket Casts says that when a submitted feed "contains the itunes:block tag set to Yes … our platform classifies the podcast as 'private,' so it will not show up in our public search database". Private podcasts can't be shared, and the share options are hidden ([Submitting Podcasts](https://support.pocketcasts.com/knowledge-base/submitting-podcasts)). The same page says a feed that shows up in search when it shouldn't is "most likely because the feed doesn't contain the itunes:block XML tag set to Yes".

**Timing matters.** If the tag is added only after the feed has been submitted, Pocket Casts "won't immediately hide the podcast from our public search database, but it will eventually do so automatically" ([Submitting Podcasts](https://support.pocketcasts.com/knowledge-base/submitting-podcasts)). So the tag has to be in `feed.xml` the first time the URL is pasted anywhere.

**The tag also stops duplicate matching.** Pocket Casts may merge a feed into an existing listing whose title, author, website URL and thumbnail URL match. `itunes:block` "will prevent our system from trying to match the feed with any others" ([Submitting Podcasts](https://support.pocketcasts.com/knowledge-base/submitting-podcasts)). It doesn't matter for a one-off personal show, but it is a second reason to set the tag.

**There is a "Private" mode, but only on the web submission form.** The form at `pocketcasts.com/submit` has a Private option so the show "won't be shared with anyone or appear in search for anyone else". It returns a short URL you paste into the app ([Private, Paid, or Members-Only Feeds](https://support.pocketcasts.com/knowledge-base/private-or-members-only-feeds), [Password Protected Podcast Feeds](https://support.pocketcasts.com/knowledge-base/password-protected-podcasts)). In-app search has no such toggle. There, `itunes:block` is the only privacy control.

**Apple's spec.** Apple defines channel-level `<itunes:block>` as: "Specifying the `<itunes:block>` tag with a Yes value, prevents the entire podcast from appearing in Apple Podcasts. Specifying any value other than Yes has no effect" ([A Podcaster's Guide to RSS](https://help.apple.com/itc/podcasts_connect/en.lproj/itcb54353390.html)). Apple tells creators of private feeds to "be sure to use the `<itunes:block>` tag so the Apple Podcasts public directory cannot process it" ([Distribute your shows](https://podcasters.apple.com/support/5108-how-apple-podcasts-distributes-your-shows-to-listeners)). Apple's tags are case-sensitive ([Podcast RSS feed requirements](https://podcasters.apple.com/support/823-podcast-requirements)), so emit exactly `<itunes:block>Yes</itunes:block>` inside `<channel>`.

### 2. Refresh

**Server polling.** "Feed changes are not picked up by our parsers immediately. On average, it can take up to 20 minutes." It can take longer depending on follow count, upload frequency and the feed's error count. "If a feed repeatedly produces errors, our servers will check it less and less often" ([Podcast Parsing](https://support.pocketcasts.com/knowledge-base/podcast-parsing/)). If errors continue long enough, Pocket Casts "will treat the podcast as permanently unavailable" ([Private, Paid, or Members-Only Feeds](https://support.pocketcasts.com/knowledge-base/private-or-members-only-feeds)).

**Push instead of poll.** Pocket Casts supports WebSub and Podping, so a feed can announce updates instead of waiting to be polled ([Podcast Parsing](https://support.pocketcasts.com/knowledge-base/podcast-parsing/)). A WebSub hub is an extra third-party service, so it is out of scope under the map's guardrails, but it is the only documented way to beat the poll interval.

**Manual refresh.** On Android and iOS 7.83+ and on web, open the podcast page and pull down, or use ⋯ → *Refresh Episode List* ([Refreshing a Podcast's Episode List](https://support.pocketcasts.com/knowledge-base/refreshing-a-podcasts-episode-list/)). In code, this asks the server to re-parse the feed (`GET api/v1/update_podcast?podcast_uuid=…&last_episode_uuid=…`) and polls until the server reports a new episode ([`RefreshService.kt`](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/servers/src/main/java/au/com/shiftyjelly/pocketcasts/servers/refresh/RefreshService.kt), [`PodcastManagerImpl.kt` L618–636](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/repositories/src/main/java/au/com/shiftyjelly/pocketcasts/repositories/podcast/PodcastManagerImpl.kt#L618-L636)). Even a forced refresh goes through Pocket Casts' servers. The phone still doesn't read the feed.

### 3. Enclosure fetching: the phone fetches the MP3s

**Pocket Casts hosts no audio.** "We do not store your episode files … listeners download or stream it from [your host]" ([Podcast Hosting](https://support.pocketcasts.com/knowledge-base/podcast-hosting)).

**Downloads go from the phone to the enclosure URL.** Before each download, Android asks Pocket Casts' cache server for the episode's current URL (`GET /mobile/episode/url/{podcast}/{episode}`) ([`PodcastCacheService.kt` L105](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/servers/src/main/java/au/com/shiftyjelly/pocketcasts/servers/podcast/PodcastCacheService.kt#L105), [`EpisodeManagerImpl.kt` L905–913](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/repositories/src/main/java/au/com/shiftyjelly/pocketcasts/repositories/podcast/EpisodeManagerImpl.kt#L905-L913)). It then opens a plain HTTP GET to that URL from the device ([`DownloadEpisodeWorker.kt` L139](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/repositories/src/main/java/au/com/shiftyjelly/pocketcasts/repositories/download/DownloadEpisodeWorker.kt#L139), [`EpisodeDownloader.kt` L75–90](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/repositories/src/main/java/au/com/shiftyjelly/pocketcasts/repositories/download/EpisodeDownloader.kt#L75-L90)). iOS builds a `URLRequest` from the episode URL, and only `http` and `https` are allowed ([`DownloadManager.swift` L485–509](https://github.com/Automattic/pocket-casts-ios/blob/bd133d328464a8e2ee792a9371c697fb568458e3/podcasts/DownloadManager.swift#L485-L509)).
- *Inferred:* the URL the server returns is the `<enclosure url>` as last parsed, not a Pocket Casts proxy URL. This fits the help center statement above, and the clients pass the URL through unchanged. The server code itself can't be checked.

**Streaming also goes from the phone to the enclosure URL.** Android re-resolves the URL the same way, then plays it through ExoPlayer on an OkHttp client on the device ([`PlaybackManager.kt` L2234–2243](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/repositories/src/main/java/au/com/shiftyjelly/pocketcasts/repositories/playback/PlaybackManager.kt#L2234-L2243), [`ExoPlayerDataSourceFactory.kt` L66](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/repositories/src/main/java/au/com/shiftyjelly/pocketcasts/repositories/playback/ExoPlayerDataSourceFactory.kt#L66)). iOS plays an `AVURLAsset` of the episode URL ([`PlaybackItem.swift` L12–17](https://github.com/Automattic/pocket-casts-ios/blob/bd133d328464a8e2ee792a9371c697fb568458e3/podcasts/PlaybackItem.swift#L12-L17)). Seeking while streaming relies on HTTP Range support at the origin. That is standard player behavior, and Apple requires "byte-range requests" for streaming ([Podcast RSS feed requirements](https://podcasters.apple.com/support/823-podcast-requirements)).

**Artwork is the exception: Pocket Casts re-hosts it.** The apps load cover art from Pocket Casts' CDN by podcast UUID (`https://static.pocketcasts.com/discover/images/webp/{size}/{uuid}.webp`), not from the feed's image URL ([`PodcastImage.kt` L6–23](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/repositories/src/main/java/au/com/shiftyjelly/pocketcasts/repositories/images/PodcastImage.kt#L6-L23), [`build.gradle.kts` L304](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/build.gradle.kts#L304)). *Inferred:* Pocket Casts' servers download `artwork.jpg` from the NAS, so it must be publicly reachable for the crawler too.

**Download validity checks (Android and iOS).** The app rejects a download whose `Content-Type` starts with `text/`, `image/`, `application/xml`, `application/rss+xml` or similar ([`EpisodeDownloader.kt` L96–98, L180–191](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/repositories/src/main/java/au/com/shiftyjelly/pocketcasts/repositories/download/EpisodeDownloader.kt#L96-L98)). It also fails any podcast episode **smaller than 150 KiB** as "suspicious" ([`EpisodeDownloader.kt` L101–108, L194](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/repositories/src/main/java/au/com/shiftyjelly/pocketcasts/repositories/download/EpisodeDownloader.kt#L101-L108)). iOS has the same 150 KiB floor ([`DownloadManager+URLSessionDelegate.swift` L11, L183–186](https://github.com/Automattic/pocket-casts-ios/blob/bd133d328464a8e2ee792a9371c697fb568458e3/podcasts/DownloadManager%2BURLSessionDelegate.swift#L11)). nginx must serve `.mp3` as `audio/mpeg`, and the Phase 1 test MP3 must be larger than 150 KiB.

**TLS.** Neither the help center nor the app code sets special TLS requirements. Android uses a stock OkHttp client ([`NetworkModule.kt` L133–138](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/servers/src/main/java/au/com/shiftyjelly/pocketcasts/servers/di/NetworkModule.kt#L133-L138)). The iOS app sets `NSAllowsArbitraryLoads` ([`podcasts-Info.plist` L149–152](https://github.com/Automattic/pocket-casts-ios/blob/bd133d328464a8e2ee792a9371c697fb568458e3/podcasts/podcasts-Info.plist#L149-L152)), so it doesn't even enforce ATS. *Inferred:* any publicly trusted certificate on 443 works for the phone. The crawler's TLS stack isn't documented.

**`*.ts.net` and unusual ports.** Pocket Casts says nothing about either. I found no primary source reporting problems with `*.ts.net`. A third-party project, [Siphon](https://github.com/cwilliams5/Siphon), says it serves feeds to Pocket Casts over Tailscale Funnel. It also serves its media tailnet-only, which only works because the phone fetches the media itself (see §3). This is anecdotal, not authoritative. *Inferred:* serving on 443 avoids any risk from non-default ports.

**Feed fields.** Pocket Casts asks for "standard RSS formats" and points to the W3C and podbase validators ([Feed Parser](https://support.pocketcasts.com/knowledge-base/about-pocket-casts-feed-parser/), [Submitting Podcasts](https://support.pocketcasts.com/knowledge-base/submitting-podcasts)). It publishes no list of required or ignored fields. Apple's requirements are the practical baseline: RSS 2.0, a unique `<enclosure>` with `url`, `length` and `type`, a stable `<guid>`, RFC 2822 `pubDate`, and HEAD and byte-range support ([Podcast RSS feed requirements](https://podcasters.apple.com/support/823-podcast-requirements)). Siphon says "Pocket Casts requires [at least one episode] for private feeds". That is unverified, but it matters for Phase 2's empty show.

## What this means for the secret-path design

- **The secret path works only if `itunes:block` is in the feed before the URL reaches Pocket Casts.** With the tag, the feed is left out of search and the share UI is turned off. Without it, the feed, and with it the secret URL, enters public search. Adding the tag later hides the feed only "eventually". `podfeed init` should always write `<itunes:block>Yes</itunes:block>`, and a test should check that the tag is there.
- **Pocket Casts keeps the secret feed URL on its servers.** It also exports feed URLs to the user (`/import/export_feed_urls`, [`ServiceManager.kt` L50–55](https://github.com/Automattic/pocket-casts-android/blob/09b46eb33c5e92833eee78ef1317def953161494/modules/services/servers/src/main/java/au/com/shiftyjelly/pocketcasts/servers/ServiceManager.kt#L50-L55)). The secret then rests on Pocket Casts' account and data security. That fits a personal feed.
- **The MP3s need the secret too.** The phone fetches each enclosure URL from the public internet, so the MP3s must be publicly reachable over HTTPS. The feed lists them by URL, so put them under the same secret prefix (`/p/<secret>/episodes/…`), not at a guessable public path. Otherwise the audio is open even though the feed isn't. `artwork.jpg` is fetched by Pocket Casts' servers, so it must be public as well. Put it under the secret prefix too.
- **No auth is required, and Basic auth adds little.** Pocket Casts' Basic-auth support is "limited", and the credentials end up in the URL anyway. The secret path gives the same protection with less to break.
- **Don't IP-allowlist the media.** The phone on cellular has an arbitrary IP. Restricting the feed path to the four crawler IPs is possible, but it isn't in scope.
- **Keep the feed URL stable.** Rotating the secret is a feed move: `itunes:new-feed-url` plus a 301, kept for at least a month. A 301 from the old path also gives the old URL away, so rotation offers less protection than it seems.

## Risks and unknowns

- **Server-side behavior can't be checked.** The parser and directory are closed source. Three points rest on the help center plus inference: that `itunes:block` keeps the feed out of every public surface, not just search; that the episode-URL endpoint returns the raw enclosure; and that the crawler re-hosts artwork.
- **Private shows may still have a public page.** Pocket Casts Web opens any feed URL through `pocketcasts.com/follow/<feed-url>`, "whether or not the podcast appears in our public directory" ([Submitting Podcasts](https://support.pocketcasts.com/knowledge-base/submitting-podcasts)). Only someone who already has the URL can do this. Whether a private show's podcast UUID page is reachable by others wasn't established.
- **The Phase 2 empty feed may not subscribe.** The "at least one episode" claim comes from a third party. Test with one real episode if the empty skeleton fails.
- **Freshness.** New episodes typically appear within about 20 minutes, sometimes longer. A pull-to-refresh asks the server to re-poll. The CLI's verify step checks the NAS, not Pocket Casts, so the skill should say the episode can take a few minutes to appear.
- **Errors slow polling.** Repeated feed errors, such as a Funnel outage or a NAS reboot, push the feed down Pocket Casts' polling schedule. Enough of them can mark it permanently unavailable.
- **The crawler's TLS, redirect and timeout behavior is undocumented.** Test it once in Phase 1/2 by watching the nginx access log for the `PocketCasts/1.0` User-Agent.
