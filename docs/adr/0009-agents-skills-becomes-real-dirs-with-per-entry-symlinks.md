# `~/.agents` and `~/.agents/skills` become real directories, with each entry symlinked individually instead of the whole directory

`docs/adr/0002-*.md` made `~/.agents` a single whole-directory symlink to `<repo>/.agents`. That worked as long as everything under `~/.agents/skills/` was something this repo curated. It stopped working once `~/.agents/skills/` became an emerging cross-agent convention that vendor CLIs write into directly: installing and authenticating Atlassian's `twg` (Teamwork Graph CLI) ran `twg skills install`, which wrote its own official skill bundle (`twg`, `twg-jira`, `twg-confluence`, and nine more) straight into `~/.agents/skills/` — and because that whole directory was one symlink into this repo, those vendor files landed inside the git working tree. A `.gitignore` pattern for `twg*` fixed that specific tool, but it's reactive: any other tool that starts writing to `.agents/skills/` (Cursor, Copilot, Rovo Dev, and others already read from it; more will likely write to it too) needs its own pattern, discovered only after it's already bitten once.

Compare: `~/.config/opencode/skills` was never symlinked wholesale — `setup.sh` only ever linked `opencode/agents`, `opencode/commands`, and two JSON files individually — so `twg`'s copy landed there as plain untracked content, no collision, no gitignore entry needed.

Decided on: apply that same pattern to `~/.agents`. `setup.sh`'s `link_dir_contents()` now makes `~/.agents` and `~/.agents/skills` real directories (migrating away from a prior whole-directory symlink by backing it up per `docs/adr/0005-*.md`'s existing convention, never deleting it) and symlinks each top-level `.agents/` entry and each `.agents/skills/<name>` skill individually. Any vendor tool can now write new, untracked entries anywhere in `~/.agents/skills/` and they physically never enter this repo's working tree — no gitignore pattern needed, for `twg` or for whatever writes there next.

`scripts/verify-setup-symlinks.sh`, run by `.github/workflows/verify-symlinks.yml` on every PR, runs `setup.sh` against a scratch `HOME` and fails the build if any `.agents/` entry or any skill under `.agents/skills/` doesn't get its own correct symlink — so `setup.sh`'s linking logic can't silently drift from the repo's actual contents (a skill added without the loop picking it up, a regression in the helper function) without a required check catching it before merge. It also re-checks the exact mistake that motivated this ADR: that no file matching `.gitignore`'s vendor-skill patterns is ever git-tracked under `.agents/skills/`.

Consequence: the `.gitignore` entries for `.agents/skills/twg/` and `.agents/skills/twg-*/` (added alongside this ADR) become dead once every machine has re-run `setup.sh` — a fresh whole-directory symlink can no longer exist to reproduce the collision they guard against. Left in place anyway: they're free insurance for anyone who pulls this change but hasn't re-run `setup.sh` yet, and `scripts/verify-setup-symlinks.sh`'s own guard check would fail loudly if that transitional window ever let something slip through. Also: making `.github/workflows/verify-symlinks.yml`'s check *required* (so it actually blocks a merge, not just reports) is a GitHub branch-protection setting, not something a workflow file can set for itself — that's a manual step for whoever administers this repo.
