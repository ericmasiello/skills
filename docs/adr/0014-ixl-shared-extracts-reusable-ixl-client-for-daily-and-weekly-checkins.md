# `ixl-client.ts` moves into a shared `_ixl-shared/` folder instead of living inside `ixl-weekly-checkin`

Building `ixl-daily-checkin` (a same-day pulse check, distinct from `ixl-weekly-checkin`'s Sunday rollup) needed the same IXL login — a fragile three-request flow (regular password, then a separate parent "secret word", documented in `ixl-client.ts`) that breaks in a new way every time IXL changes its login page, per docs/adr/0012-*.md. Duplicating that ~300-line client into a second skill folder would mean two places to fix the same breakage, with no guarantee a fix applied to one copy ever reaches the other.

Decided on: move `ixl-client.ts` out of `ixl-weekly-checkin/` into a new non-skill folder, `.agents/skills/_ixl-shared/`, and have both `ixl-weekly-checkin` and `ixl-daily-checkin` import it via a relative path (`../_ixl-shared/ixl-client.ts`). This mirrors the convention already established by `_studio-shared/LABELS.md` (studio-\* skills) and `_ericmasiello-shared/LOAD-DOCS-AGENTS.md` (per docs/adr/0013-\*.md): an underscore-prefixed folder under `.agents/skills/` with no `SKILL.md`, never invoked directly, picked up by `setup.sh`'s existing per-entry symlink loop with no script changes needed. The shared IXL login credentials (`IXL_EMAIL`, `IXL_PASSWORD`, `IXL_PARENT_PASSWORD`) moved into `_ixl-shared/.env` alongside it — one login to maintain, not two — while `ixl-weekly-checkin`'s own `.env` keeps only its Google Sheets credentials, which `ixl-daily-checkin` has no reason to touch. `_ixl-shared/` carries its own minimal `package.json` (`"type": "module"`) purely so `tsc` resolves the file's module kind correctly when a caller's `tsconfig.json` reaches across the folder boundary to typecheck it — confirmed necessary live; without it `tsc --noEmit` in `ixl-weekly-checkin` failed on the imported file with a CommonJS/`verbatimModuleSyntax` error.

Consequence: `_ixl-shared/` is a real dependency, not an optional helper — both skills are broken without it, the same relationship `CONTEXT.md`'s "Companion agent" vocabulary already describes for a skill and its subagent, just for a plain shared code file instead. Each skill's own `SETUP.md`/`SKILL.md` says so explicitly (import path, `.env` location) so that dependency is discoverable by reading either skill, not just assumed from the folder name.
