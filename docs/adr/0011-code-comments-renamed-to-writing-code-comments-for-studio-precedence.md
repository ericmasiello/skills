# `code-comments` renamed to `writing-code-comments` so Studio's project skill takes precedence

This repo's `code-comments` skill and the Studio monorepo's own `~/Sites/studio/.agents/skills/writing-code-comments/SKILL.md` (Project-scope, tuned to Studio's TypeScript/React/MobX conventions) cover the same job: writing and improving code comments. Working inside Studio, both are visible to the agent at once — this repo's at User-scope (`~/.agents/skills/`), Studio's at Project-scope — but nothing forced the Studio-specific one to win. The two different names meant they were just two independent candidates for the agent to pick between by description match, not a shadowing pair.

Decided to rename this repo's skill, directory and frontmatter `name` both, from `code-comments` to `writing-code-comments` — an exact match with Studio's. That turns the pairing into the plugin's documented scope-priority merge (project > user > opencode > builtin) for two skills sharing one name: inside Studio, Studio's Project-scope version shadows this repo's User-scope one outright. Outside Studio, the renamed skill still works from `~/.agents/skills/writing-code-comments/`, just invoked by its new name.

Consequence: the old `/code-comments` invocation is gone — `.agents/README.md`'s catalog entry was updated to `writing-code-comments` alongside the rename. If Studio's skill is ever renamed on that side, this pairing breaks silently with no error, since a name mismatch just makes both skills coexist as unrelated candidates again; check `~/Sites/studio/.agents/skills/` before renaming either one. Unlike the `playwright` skill's builtin-provider gate (`docs/adr/0007-*.md`), there's no extra matching gate to satisfy here — this relies on the plugin's plain scope-priority merge, which applies to any two identically-named skills regardless of what they're named.
