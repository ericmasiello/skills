# `agent-browser` replaces the `playwright` skill, and `disabled_skills` turns the builtin off

`docs/adr/0007-*.md` kept a user-scope `playwright` skill so that browser work would go to `playwright-cli` in a real, headed Chrome instead of `openchamber_web`. That ADR also says the plugin's provider filter covers a discovered skill named `agent-browser`. It doesn't. In `oh-my-openagent` 5.1.19 the filter in `getAllSkills` is `new Set(["playwright"])`, and the one in `skill-context.ts` is `new Set(["dev-browser", "playwright"])`. A discovered `agent-browser` skill passes both and loads next to `playwright`. Their descriptions contradict each other ("MUST USE for any browser automation" and "Prefer agent-browser over any built-in browser automation"), so the model picks one at random. That is the same nondeterminism 0007 set out to remove.

The reason to keep `playwright` was its headed, logged-in defaults, but `agent-browser` 0.43 covers them: `--headed`, `--profile`, `--restore`, `state save`/`state load`, `--auto-connect` to a running Chrome, and `--executable-path` for installed Google Chrome (tested). It drives a real Chrome over CDP, so it also meets 0007's original goal of never using an embedded browser. On the same page with the browser already running, it took about 200 ms to navigate and snapshot, against about 720 ms for `playwright-cli`. Its interactive-only snapshot (`snapshot -i`) was about 40% of the size of `playwright-cli`'s full snapshot, which has no equivalent filter. The only real gap is engines: `agent-browser` runs Chrome only (plus Safari through WebDriver), while Playwright also runs Firefox and WebKit.

Setting `browser_automation_engine.provider` to `"agent-browser"` is not an option. The schema enum is `playwright`, `dev-browser` and `playwright-cli`, and the builtin table has no `agent-browser` entry.

Decided on: `agent-browser` is the only browser skill. It is synced from `vercel-labs/agent-browser` through `npx skills` and tracked in `.skill-lock.json`. Its `SKILL.md` is upstream's stub, which loads the usage guide matching the installed CLI with `agent-browser skills get core`, so it stays unedited and `npx skills update` can sync it. The user-scope `playwright` override is deleted. `opencode/oh-my-openagent.json` sets `"disabled_skills": ["playwright"]`, which removes the builtin `playwright` skill whatever the provider value. `browser_automation_engine` is removed because its only job was 0007's name match. `playwright-cli` stays an optional, manually used fallback for Firefox and WebKit, and no skill calls it.

Consequence: with no `playwright` skill loaded, the plugin's Sisyphus prompt falls back from "load the `playwright` skill" to "use the available browser automation surface", which leads to `agent-browser`. If a plugin update adds `agent-browser` to a provider filter, or ships a builtin of that name, check this ADR again: the discovered skill could then be dropped silently, as 0007 describes for `playwright`. 0007's statement about `agent-browser` was wrong when written for this plugin version, and this ADR supersedes 0007.
