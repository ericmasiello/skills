# `vista-atlassian` moves from `acli` + Rovo MCP fallback to the official `twg` CLI as its sole primary tool

Atlassian shipped `twg` (Teamwork Graph CLI, `developer.atlassian.com/cloud/twg-cli/`) to GA in mid-2026: a first-party, agent-first CLI that Atlassian's own FAQ explicitly positions as `acli`'s agent-facing successor ("Atlassian CLI was built for human-driven administration before agentic usage was common. Teamwork Graph CLI is purpose-built as an agent-first CLI..."). Verified directly against Atlassian's live docs, support pages, the public `atlassian/twg-cli` GitHub org, and its real install script — not taken on faith from a single research pass, because an early background-research summary of this same tool read exactly like a plausible LLM confabulation (suspiciously complete command tables, unverifiable precise dates) before independent verification confirmed it was real.

`vista-atlassian` previously split its work across two tools because neither alone covered both products for our use case: `acli` for Jira CRUD/transitions/comments (but only page-view for Confluence) and the Rovo MCP server (`io.vista/atlassian-mcp` — the skill had actually been referencing a nonexistent `io.vista/atlassian-rovo-mcp` name) for everything Confluence-write and CQL-search related. `twg`'s command catalog covers both halves directly and for free (`twg jira workitem *`, `twg confluence content *`, `twg confluence search query` for CQL) — the acli/MCP split this skill depended on no longer reflects a real tooling gap.

Decided on:
- `twg` becomes the skill's only primary tool. Rovo MCP is now a true fallback (only reached for if `twg` isn't installed/authenticated in the current environment), not a required second tool for routine Confluence work.
- Deleted `vista-atlassian/REFERENCE.md` (the acli/MCP command dump) rather than rewriting it into a `twg` version. `twg`'s own docs explicitly tell agents to discover command syntax live (`twg help`, `twg help describe "<path>"`) instead of memorizing it, because the command surface is large and evolves independently of any skill that might hardcode it. A static reference file would just be a second, slower-to-update copy of the same self-discovery the CLI already provides — the discipline here is not maintaining a manually-synced catalog that already has a canonical, self-updating source.
- `twg setup` installs Atlassian's own official skill bundle to `~/.agents/skills/twg*` (`twg-jira`, `twg-confluence`, `twg-context-discovery`, etc.) automatically. `vista-atlassian`'s remaining job is narrow: pin the Vistaprint-specific site (`vistaprint.atlassian.net`) and hand off command discovery to that bundle rather than duplicating it.
- Updated `README.md`'s Prerequisites table and `setup.sh`'s CLI check from `acli` to `twg`.

Consequence — deliberately left open, not resolved here: the separate, upstream-synced `atlassian-mcp` skill (from `jeffallan/claude-skills`, tracked in `.agents/.skill-lock.json`) covers generic Jira/Confluence-via-MCP guidance that plausibly overlaps with what `twg`'s own official skill bundle now provides. It was **not** touched in this change — editing a skill tracked in `.skill-lock.json` by hand desyncs its `skillFolderHash` from upstream, and a proper Legacy/Needs-review call (per `CONTEXT.md`'s vocabulary) needs a real side-by-side comparison against `twg`'s bundle, not a guess made in passing while migrating an unrelated skill. Follow-up: run that comparison and decide via the normal `npx skills` flow, not a direct file edit.
