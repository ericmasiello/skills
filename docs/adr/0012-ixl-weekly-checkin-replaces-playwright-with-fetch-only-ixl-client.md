# `ixl-weekly-checkin` replaces Playwright/UI-scraping with a fetch-only IXL client

**Status:** accepted

`ixl-weekly-checkin` originally logged into IXL with Playwright, navigated the Usage Details, Score Chart, and Diagnostic pages, and scraped the rendered DOM (plus a full-page screenshot read by a multimodal model for the Diagnostic levels, since those render as chart labels with no accessible text). The skill's own `SKILL.md` carried a note that this was deliberate. An earlier attempt to script around the Score Chart's PDF export "failed outright," so reading the rendered page was judged the more reliable path.

That earlier failure was specific to the PDF export, not to scripting IXL in general. Reverse-engineering the network requests IXL's own pages fire (via Chrome DevTools, documented live against the real account) found that Usage Details, Score Chart, and Diagnostic stats are each backed by a plain JSON endpoint, and that the full three-step parent login (`/signin` → `/signin/ajax/page` → `/signin/subaccount`) can be replayed with nothing but a cookie jar and `fetch`. No browser engine is involved at all. This was validated end-to-end against the family's real tracker sheet. All 146 historical raw-log rows reconstructed from the API matched the sheet exactly, and a diagnostic-level discrepancy the API caught (a still-resolving range narrowing) was confirmed correct, not a bug.

Decided on: `ixl-client.ts` is now the skill's single login/data client, used by `collect-weekly-data.ts` (replaces the old Playwright-driven collection steps) and `validate-against-sheet.ts` (an ongoing accuracy check, not part of the regular weekly run). `update-weekly-log.ts` (the Sheets-write side) is untouched. Every request through this client waits a randomized human-scale delay first, so the traffic doesn't look like a script running flat out. The exact endpoint URLs, request/response shapes, that pacing, and the two schema quirks found along the way (a still-resolving diagnostic returns `{min, max}` instead of a firm `score`; `score-chart/run`'s valid `grades` are `-2`/`0`/`1`-`12`, not `-1`) live as comments in `ixl-client.ts` itself. This ADR records the decision, not the API reference.

Consequences:
- More stable day to day, though not instant anymore. No browser launch, no DOM/accessibility-tree dependency to break when IXL redesigns a page, no screenshot-plus-vision round trip for the Diagnostic levels. The deliberate per-request pacing adds real wall-clock time (a six-request pull went from under two seconds to roughly thirteen in testing); that's a chosen trade, not an oversight.
- Less resilient to a login failure. There's no browser session to fall back to and manually re-authenticate in. If IXL changes its login page, adds a CAPTCHA, or demands 2FA mid-flow, `collect-weekly-data.ts` throws and stops. A human has to check the account directly, same as before, but now without a half-finished Playwright session to inspect.
- These are undocumented, internal endpoints, not a published API. IXL can change them without notice, the same exposure the previous UI-scraping approach had to IXL changing its page markup instead.
