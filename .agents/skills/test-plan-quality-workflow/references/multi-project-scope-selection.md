# Multi-Project Acceptance-First Scope Selection

## Purpose

Give `test-plan-quality-workflow` (and anyone invoking a Stage 3 skill directly without a pre-chosen target) a deterministic way to pick where to start when a workspace contains multiple projects/modules, so the user is rarely asked "which one?". Always bias toward the acceptance layer (outermost, widest behavioral net) first, swept across the whole workspace, before drilling into unit/integration work in any single module.

This file governs **Step -1** of `test-plan-quality-workflow` — the workspace-level "which module" decision that happens _before_ a module is routed into Scenario A or B. It is a different granularity than `test-analyze-testability-blockers` Part B, which ranks candidate _classes/components within_ a Scenario B (legacy, no-tests) module by business-criticality/change-frequency/testability-effort. Use this file first to pick the module; use that skill's Part B once you're inside a legacy module with several untested classes to rank _those_.

## When This Applies

- A solution/monorepo with more than one source project and/or more than one test project.
- A single codebase split into layered assemblies/packages (e.g. Domain / Application / Persistence / Api), each with its own test project.
- Ambiguous requests like "improve test quality" or "start outside-in" with no named target.
- Requests that explicitly ask to figure out the best layer/project to start from (treat this as an instruction to run this procedure, not as a question to bounce back to the user).

## Algorithm

### Step 1 — Enumerate modules

Find the unit of "a project" for the platform:

- **.NET**: every `*.csproj` referenced by the `.sln`; pair each non-test project with its `*.Tests.csproj` (by name convention or `ProjectReference`).
- **Node/TS**: each `package.json` in a workspace/monorepo, or top-level `src`/`test` folder pairs.
- **Python**: each `pyproject.toml`/`setup.py` package, paired with its `tests/` folder.
- Anything else: top-level folders that contain both source and a recognizable test runner config.

Record, per module: source path, test project path (or **none**), and language/test framework. A module with no test project at all is itself the strongest signal found so far — do not treat "no test project" as "nothing to report," it is the answer.

### Step 2 — Gather cheap evidence (reuse before generating)

Check these, cheapest and most authoritative first. Only look for what already exists — do not run a full test/coverage/mutation suite yet:

1. Repo-scoped memory notes (e.g. this assistant's `/memories/repo/` files), if the tooling in use has them. They are the cheapest source — no tool calls beyond viewing the file — and may already contain a prior session's endpoint sweep, gap list, or baseline-doc caveat for this exact repo. Treat a prior sweep as a strong prior, not an unconditional truth: if it's dated, or the relevant controllers/routes have changed since, re-verify the specific claims before reporting them as current, and update the memory note either way (confirmed-still-true or corrected).
2. Existing coverage or mutation artifacts (e.g. `**/StrykerOutput/**/reports/*.json`, coverage XML/lcov, a committed baseline/quality doc such as a `quality-baseline.md`). Use the **freshest** one per module. Treat these as a starting hint, not ground truth: a baseline/coverage doc is often generated by running only one test project's suite, so it can both miss real gaps (nothing flagged there is untested) and falsely flag gaps that are actually covered by tests living in a *different* test project (e.g. an HTTP-level test in an Api.Tests project exercising an Application-layer workflow the doc never saw). Before relying on such a doc to conclude a layer is complete, spot-check a sample of its claims directly against test files, and if the module is small enough, enumerate its full driving surface (every REST endpoint or public use-case entry point) instead of trusting the doc's list alone.
3. Git signal: current branch name and the last 10-20 commit subjects. Keywords like `test`, `coverage`, `mutation` plus a module name are a strong hint about which module is already mid-flight.
4. Structural signal: does a test project/folder exist for this module **at all**? Zero test project outranks every other signal — every layer, including acceptance, is unprotected.
5. Test-to-source file/line ratio as a last, weakest signal, only when nothing above is available.

Stop gathering as soon as you can rank confidently — this is meant to be cheap, not exhaustive. Prefer a handful of terminal/grep/file-search calls over reading every source file.

### Step 3 — Classify each module's acceptance-layer state

For each module, classify using whichever evidence was found:

- `NONE` — no test project exists at all, or the entry-point/use-case layer has no test referencing it (mutation shows `NoCoverage` on every mutant of that class, or zero test files mention the class name).
- `THEATER` — a test exists and executes the use case, but with weak/absent assertions (mutants execute — not `NoCoverage` — yet the mutation score is still ~0%).
- `PARTIAL` — some behaviors protected; mutation/coverage score below the project's own "low" threshold.
- `PROTECTED` — meets or exceeds the project's own thresholds; only Stage 4 triage remains.

### Step 3.5 — Verify with a full driving-surface sweep before trusting Step 3's classification

A workflow-level or per-project coverage baseline can look `PROTECTED` while individual driving entry points are actually `NONE`. This applies to any kind of driving surface, not just REST APIs — the same blind spot exists for CLI commands, message/event consumer handlers, gRPC/RPC service methods, scheduled jobs, and public library API functions. Before reporting a module's acceptance layer as complete:

1. Enumerate every entry point for the module's actual interface type:
   - REST/HTTP API: grep controllers for the framework's route attributes/decorators (e.g. `\[Http(Get|Post|Put|Patch|Delete)` for ASP.NET Core, `@(Get|Post|Put|Delete|Patch)Mapping` for Spring, `router\.(get|post|put|delete)` for Express) to get a full verb+route list.
   - CLI: grep for command registration (subcommand names, argument parser definitions).
   - Message/event consumers: grep for handler registrations, topic/queue subscriptions, or `[Consumes]`-style attributes.
   - Public library API: grep for exported/public top-level functions or classes intended as the package's entry points.
   - Do not rely on remembering "the main ones" — list all of them.
2. For each entry point, grep the acceptance/driving-level test project for that literal identifier (route fragment, command name, handler class, exported function name) to find which test file(s), if any, call it. Do this as **one combined regex-alternation search** (`identifier1|identifier2|identifier3|...`) across the test project, not a separate grep call per entry point — a loop of dozens of individual searches burns tool calls/time for no extra accuracy. Only fall back to per-item searches for the handful of entry points the combined pass left ambiguous (e.g. built via a URI builder rather than a literal string).
3. Mark each entry point `Covered` (positive + at least one negative/failure case found) or `Gap` (zero test calls found). For HTTP APIs specifically, watch for routes built via `UriBuilder`/helper methods rather than literal strings in the client call — grep for the route segment assigned to `Path =` or similar builder properties too, not just literal call sites.
4. Report the gap list as concrete entry-point identifiers (verb+route, command name, handler name, etc.), not a percentage. A workflow or class name being "tested" at an inner layer does not mean its driving entry point is exercised — the entry-point wiring (routing/parsing, model binding, status/exit codes) is a distinct, separately-testable behavior.

This full sweep is cheap (a small, batched set of grep calls — not one call per entry point) and is the only reliable way to confirm "every entry point has acceptance coverage" on the very first run, with no prior memory to lean on — spot-checking the workflows a coverage doc happens to flag is not equivalent and can both over- and under-state the real gap.

### Step 4 — Rank and select

Rank modules `NONE` > `THEATER` > `PARTIAL` > `PROTECTED`. Within a tie, prefer, in order:

1. the module/use-case flagged business-critical in existing docs or comments
2. the one with the larger behavior/mutant count (bigger blast radius if left unprotected)
3. the one implicated by the current git branch/commit signal

Select the top-ranked module (and, within it, the top-ranked use case(s)) as the Stage 3a acceptance target. Carry the full ranked list into the Required Decision Output so the choice is auditable even though the user wasn't asked.

### Step 5 — Sweep before you dive

Apply the outside-in rule at the workspace level: finish, or at least sample, the acceptance-layer sweep across the top few ranked modules before spending Stage 3b/3c/Stage 2/Stage 4 effort deep in just one of them — unless the user explicitly asked to focus on a single module. A handful of zero-coverage use cases fixed across three modules is worth more than one module taken from 60% to 90% while a sibling module still sits at 0% acceptance coverage.

## When You Still Must Ask

Only fall back to a clarifying question when:

- no enumeration mechanism is available (can't list files or run terminal commands) and the request is genuinely ambiguous, or
- two or more modules are tied on every evidence signal above **and** the choice materially changes scope/cost (e.g. one path implies standing up a whole new test project), or
- the user's own phrasing already named a specific module/file — then confirm quickly rather than re-deriving it, don't re-litigate a target that was already given.

Even then, ask **one** targeted question with the ranked candidates already shown as options, rather than an open "what should I work on?".

## Worked Example (generalized from a real session)

A .NET solution had five backend projects (Domain, Application, Api, ProductFacade, Persistence) but only four had test projects — Persistence had **none**. Evidence gathered in under a minute using only terminal/grep/file-search calls:

- A committed `quality-baseline.md` inside the Application test project, dated days earlier, documented per-class mutation scores.
- The current git branch was named `test/mutation-testing-and-coverage-baseline`, and recent commits already touched Application's tests extensively.
- Stryker mutation reports existed for Application/Domain/ProductFacade (Application had by far the most iterations); Api's report was never completed; Persistence had no report and no test project at all.

Ranking: Persistence (`NONE` — no test project) ranked highest in the abstract, but its adapters are only reachable as the **mocked boundary** of Application's use cases, not as a standalone acceptance target — acceptance tests exercise use cases, not adapters directly. So the acceptance sweep correctly started in Application, on the two use cases with literal `NoCoverage` on every mutant, and Persistence's missing integration-test project was flagged as the very next handoff instead of silently skipped. No clarifying question was needed to reach this ranking — one was still asked in that session because this heuristic did not exist yet. That is exactly the gap this file closes.

## Anti-Patterns

- ❌ Asking "which project should I start with?" as the first move when reports, branch name, or git history already answer it.
- ❌ Picking the module mentioned most recently in chat instead of the one with the widest evidenced gap.
- ❌ Finishing all 4 stages in one module before checking whether a sibling module has zero acceptance coverage.
- ❌ Treating "no test project exists" as lower priority than "tests exist but are weak" — absence is the widest gap, not a reason to defer it.
- ❌ Trying to write an "acceptance test" directly against a driven adapter (repository/external client) just because it's the `NONE`-ranked module — adapters are exercised by integration tests; hand that module to `test-generate-integration-tests` instead once the use case that mocks it has acceptance coverage.
- ❌ Declaring the acceptance layer "complete" after spot-checking only the handful of workflows/use-cases a coverage/quality-baseline doc happened to flag, instead of enumerating the full driving surface (every REST endpoint or public use-case entry point) and checking each independently. A per-project-scoped baseline doc is neither exhaustive nor always accurate — a real session found 12 of 51 REST endpoints with zero acceptance-level test after such an enumeration, despite the baseline doc implying only a handful of workflows were untested.
